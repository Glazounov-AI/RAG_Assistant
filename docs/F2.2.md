# F2.2 — structured registry MVP

Opt-in catalog per profile; legacy profiles stay semantic. JSON in a leading `<!-- object` comment followed by a newline and closed by `-->` defines object_id, object_type, title, summary and configured filter fields. Untagged documents remain semantic only. Registry is rebuilt transactionally per mode at startup, under RAG_DB_DIR/objects/registry.db. Invalid headers fail startup rather than silently returning incomplete data. Counts refer to registered objects, not all documents or all projects on the website. Restart after edits. Structured responses bypass LLM and cache. Exact case-insensitive filters; no inferred technologies. Portfolio tags cover five existing project documents; technology metadata is provisional and not exhaustive. Service Desk remains semantic. Supported grammar: `сколько проектов`, `список проектов`, `все проекты`, `список проектов страница 2`, `проекты по technologies: Python`, `проекты по category: rag`. Ambiguous queries remain semantic. API adds strategy, total, page. New strategies require registering a handler and extending routing/validation. No domain classifier or PostgreSQL migration. Registry reads all metadata for a mode in MVP; SQL-side filtering is future optimization. Structured requests do not apply LLM system prompts; enable only for explicitly public catalog data. No paid requests needed for registry tests.

## Final adjustments

Python filter still returns two documented projects. Profile-specific query_aliases support explicit count/list phrases and filter prefixes with configured value allowlists; other phrases fall back to semantic. Explicit field syntax remains available for arbitrary values. No claim of exhaustive natural language understanding. No changes to rate limiting, storage or Service Desk.
