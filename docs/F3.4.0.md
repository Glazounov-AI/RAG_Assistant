# F3.4.0 — Structured generation

Target Python 3.14.4. POST /generate accepts {"profile":"demo","input":{"message":"VPN"}}. Server-owned profiles define prompt, schema, model and limits. Configure RAG_GENERATION_PROFILES_DIR to examples/generation/profiles for a neutral demo. Set RAG_GENERATION_ACCESS_KEY to a separate secret; send X-Generation-Key on every generation request. If existing API auth is enabled, also send X-API-Key. The generation key grants access to all configured generation profiles; per-client profile ACLs remain required before public deployment. No profile directory means no generation profiles. No changes to retrieval pipeline or GigaChat. Existing application startup still initializes retrieval infrastructure.

The provider uses strict Structured Outputs, no retries, no retrieval or cache. Local Draft202012 validation is additional to provider validation; provider supports a subset of JSON Schema and unsupported schemas/models may fail at runtime. Input limit counts serialized JSON characters, not tokens or HTTP body bytes. Timeout is SDK request timeout, not a global wall-clock deadline. Logs use existing SQLite logger, redacted by default, successful operations only. Failed provider calls may still incur cost. Keep profile files trusted and local. Never enable content logging for sensitive tasks. The existing global rate-limit switch also controls generation limits. No public exposure until access control and request-size protections are complete.

Acceptance: run full pytest on Python 3.14.4; run a real demo request separately. Local build environment lacks OpenAI and ChromaDB and cannot download them, so full regression and provider integration are not verified here.

### Architectural acceptance

Structured Generation operates independently of retrieval,
embeddings, the structured registry and response caching.

Existing semantic RAG and structured registry functionality
remain operational.

The generation mechanism is domain-independent.
Service Desk classification and business rules remain
in the external application.

### Remaining limitations

- Performance measurements are preliminary.
- Production latency and p95 are not established.
- Real-provider integration used one JSON Schema.
- Combined API and generation authentication requires
  additional integration coverage.
- Validation errors require sensitive-data leakage protection.
- Per-client generation profile permissions are not implemented.
- Provider failure observability and coordinated timeouts
  require further work.
- Failed generation attempts are not fully covered by
  persistent usage logging.

Security limitations must be addressed before public deployment.
