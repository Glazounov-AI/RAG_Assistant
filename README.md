# RAG Assistant

**RAG Assistant** — работающая система Retrieval-Augmented Generation (RAG) для ответов на вопросы по собственным документам. Основной продукт проекта — `assistant_api`: Python-приложение с OpenAI, векторным поиском ChromaDB, HTTP API на FastAPI, SQLite-кешем, журналом запросов и несколькими независимыми базами знаний.

Система развёрнута как отдельный backend на Railway и интегрирована с AI-консультантом сайта [Glazounov AI Lab](https://glazounov-ai.ru/). Открытая документация HTTP API: [Swagger UI](https://ragassistant-production-6923.up.railway.app/docs).

> **Область документации.** Все основные разделы ниже относятся к `assistant_api`. Описывается функциональность, присутствующая в исходном коде ветки `main`; фактический набор возможностей конкретного production deployment следует проверять отдельно. Наличие кода или теста не заменяет проверку развёрнутого сервиса.

## Возможности

- **Несколько баз знаний:** режимы `support` (техническая поддержка) и `portfolio` (проекты и услуги) с независимыми коллекциями ChromaDB.
- **Управление документами:** индексация `.txt`, `.md`, `.markdown`; синхронизация добавлений, изменений и удалений; контроль ревизий и параметров индексации.
- **RAG-пайплайн:** построение embeddings вопроса, поиск релевантных фрагментов, формирование контекста и генерация ответа через OpenAI.
- **Версионный кеш:** SQLite-кеш разделён по режиму и фактической версии индекса; изменение индекса приводит к использованию другого ключа кеша.
- **HTTP API и CLI:** FastAPI для внешних клиентов и отдельное консольное приложение поверх одного RAG-пайплайна.
- **Контроль доступа:** опциональная проверка `X-API-Key`, валидация входных данных и SQLite rate limiter.
- **Наблюдаемость:** журнал вопросов, ответов, попаданий в кеш и времени обработки.
- **Постоянное хранение:** ChromaDB и SQLite на Railway Volume через `RAG_DB_DIR`.
- **Проверки:** автоматизированные тесты API, авторизации, лимитов, синхронизации документов и сценариев отказов.

## Базы знаний и управление индексом

Режим задаётся полем `mode` запроса. По умолчанию используется `support`.

| Режим | Исходные документы | Коллекция ChromaDB | Максимум символов в вопросе | Лимит API |
|---|---|---|---:|---:|
| `support` | `assistant_api/data/` | `api_rag_collection` | 2 000 | 10/мин |
| `portfolio` | `assistant_api/data/portfolio/` | `portfolio_kb` | 8 000 | 5/мин |

Лимиты применяются по сочетанию идентификатора клиента и режима, если `RAG_RATE_LIMIT_ENABLED=true`. Значения заданы в `KNOWLEDGE_BASES` (`assistant_api/config.py`).

При инициализации RAG-пайплайна обе базы синхронизируются с документами на диске. Индексатор:

1. Находит поддерживаемые файлы и вычисляет SHA-256 содержимого.
2. Сопоставляет хеш документа и хеш параметров индексации с метаданными существующих чанков.
3. При необходимости разбивает текст на фрагменты и создаёт embeddings.
4. Записывает новую ревизию перед удалением старой; при ошибке записи пытается очистить новые чанки.
5. Удаляет устаревшие ревизии и записи документов, отсутствующих в исходном каталоге.

Дополнительно проверяется полнота ревизии по числу и идентификаторам чанков. Если каталог базы знаний внезапно пуст, массовое удаление проиндексированных документов блокируется.

**Ограничение:** переключение ревизий не является единой транзакцией ChromaDB. Предусмотрены защитные проверки и восстановление отдельных сценариев сбоев, но не гарантируется атомарное обновление индекса при любом отказе.

Версия индекса вычисляется по сохранённым идентификаторам чанков и метаданным. Поэтому кеш ответов учитывает не только вопрос, но и режим, и актуальную версию индекса.

## RAG-пайплайн и модели

Текущие настройки `assistant_api/config.py`:

| Параметр | Значение |
|---|---|
| Генерация | `gpt-4o-mini` |
| Embeddings | `text-embedding-3-small` |
| `TOP_K` | 3 |
| `CHUNK_SIZE` | 500 символов |
| `CHUNK_OVERLAP` | 100 символов |
| `MIN_CHUNK_SIZE` | 50 символов |
| `TEMPERATURE` | 0.3 |
| `MAX_TOKENS` | 500 |

Разбиение ориентируется на абзацы и предложения с перекрытием соседних фрагментов. В ChromaDB используется пространство косинусного расстояния. Для `portfolio` задан отдельный системный промпт, запрещающий выдумывать проекты, клиентов и результаты внедрений.

**Ограничения качества:** поиск возвращает до `TOP_K` фрагментов без отдельного порога релевантности и reranking. Системные инструкции снижают риск неподтверждённых ответов, но не гарантируют отсутствие ошибок модели. Метрики качества необходимо подтверждать независимым оценочным набором.

## HTTP API

HTTP-интерфейс реализован только для основной системы `assistant_api`.

### `GET /health`

Возвращает:

~~~json
{"status":"ok","service":"rag-assistant-api"}
~~~

Проверяет доступность HTTP-сервиса, но не выполняет запрос к OpenAI и не подтверждает качество поиска или готовность внешних зависимостей.

### `POST /query`

Пример запроса:

~~~json
{
  "query": "Какие проекты представлены в портфолио?",
  "mode": "portfolio"
}
~~~

Успешный ответ содержит `query`, `answer`, `from_cache`, `model`. Поле `mode` необязательно; допустимы `support` и `portfolio`.

| HTTP-код | Значение |
|---|---|
| `200` | Запрос обработан |
| `401` | API-ключ отсутствует или неверен при включённой авторизации |
| `422` | Ошибка валидации запроса |
| `429` | Превышен лимит запросов |
| `500` | Ошибка обработки внутри RAG-пайплайна |

Внутреннее исключение не передаётся клиенту как текст ошибки. Обработка запросов и журналирование разделены: ошибка записи лога не прерывает успешный ответ.

### Безопасность

Для публичного сервиса следует включить:

~~~dotenv
RAG_API_AUTH_ENABLED=true
RAG_API_ACCESS_KEY=<длинный-секретный-ключ>
RAG_RATE_LIMIT_ENABLED=true
~~~

Ключ передаётся заголовком `X-API-Key` и проверяется перед rate limiter и RAG-обработкой. По умолчанию авторизация **выключена**: `RAG_API_AUTH_ENABLED=false`; для публичного развёртывания это необходимо изменить явно. При включённой авторизации без настроенного ключа приложение не запускается.

Не размещайте ключ OpenAI или ключ доступа к backend в браузерном JavaScript и Git. Интеграция сайта использует серверный PHP-прокси. Лимитирование по IP не заменяет полноценную защиту от злоупотреблений, особенно при работе за прокси или NAT.

## Установка и локальный запуск

Требуется Python и ключ OpenAI. В репозитории используется окружение Python 3.14; совместимость конкретных версий зависимостей проверяйте при установке.

~~~powershell
git clone https://github.com/Glazounov-AI/RAG_Assistant.git
cd RAG_Assistant

py -3.14 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

Copy-Item .env_example .env
~~~

В `.env` задайте `OPENAI_API_KEY`. Файл с секретами не должен попадать в Git. Остальные параметры задаются через окружение и `assistant_api/config.py`.

HTTP API:

~~~powershell
cd assistant_api
python -m uvicorn api:app --host 127.0.0.1 --port 8000
~~~

После запуска доступны `http://127.0.0.1:8000/health` и `http://127.0.0.1:8000/docs`.

Пример запроса из PowerShell (при включённой авторизации добавьте `X-API-Key`):

~~~powershell
$body = @{ query = "Что такое RAG?"; mode = "support" } | ConvertTo-Json
Invoke-RestMethod -Uri "http://127.0.0.1:8000/query" -Method Post -ContentType "application/json" -Body $body
~~~

Консольное приложение запускается из `assistant_api` командой `python app.py`. Команды консоли: `stats`, `clear`, `exit` / `quit`.

## Хранение, кеш и журналирование

По умолчанию данные основной редакции сохраняются в `assistant_api/db/`. Переменная `RAG_DB_DIR` переопределяет корневой каталог:

~~~text
db/
├── cache/rag_cache.db
├── logs/logs.db
├── chromadb/
└── rate_limits/rate_limits.db
~~~

**Кеш** хранит ответ и контекст. Ключ формируется с учётом нормализованного вопроса, режима и версии индекса. Повторный запрос к неизменённой базе знаний может обслуживаться без нового вызова LLM.

**Журнал** сохраняет вопрос, ответ, признак попадания в кеш, время обработки, источник и служебные поля пользователя. Для HTTP API источник — `api`; в текущем интерфейсе `user_id` и `username` не заполняются. Запись вопросов и ответов требует учитывать конфиденциальность данных и политику хранения логов.

**Rate limiter** использует отдельную SQLite-базу и фиксированные минутные окна. Для производственных нагрузок с несколькими экземплярами приложения ограничения и конкурентный доступ к хранилищу требуют дополнительной оценки.

## Railway и интеграция с сайтом

Основной FastAPI backend развёрнут на Railway:

- API: https://ragassistant-production-6923.up.railway.app
- Проверка доступности: https://ragassistant-production-6923.up.railway.app/health
- Документация: https://ragassistant-production-6923.up.railway.app/docs

Команда запуска из каталога `assistant_api`:

~~~bash
python -m uvicorn api:app --host 0.0.0.0 --port $PORT
~~~

Для постоянного хранения подключён Railway Volume с путём монтирования `/data`; настройка приложения:

~~~dotenv
RAG_DB_DIR=/data/db
~~~

На Volume сохраняются SQLite-кеш, логи, лимиты и данные ChromaDB. Это позволяет сохранять состояние при обычном redeploy при условии, что Volume подключён и путь не изменён. **Volume не является независимой резервной копией.**

### Проверенная миграция данных — 13 октября 2026 года

При миграции с файловой системы контейнера на Railway Volume выполнены предварительное резервное копирование, перенос хранилищ, проверки целостности SQLite и контроль идентификаторов документов ChromaDB.

Подтверждено на момент проверки:

- `PRAGMA integrity_check = ok` для SQLite-файлов кеша, логов и ChromaDB;
- доступность коллекции `api_rag_collection` и наличие 15 документов;
- совпадение количества и SHA-256 отсортированных идентификаторов документов до и после переноса;
- `GET /health` и `POST /query` возвращали HTTP 200;
- повторный запрос обслуживался из кеша;
- новые записи логов создавались на Volume.

Эти результаты относятся к **проверке миграции 13 октября**, а не к непрерывному мониторингу текущего состояния. Предварительный архив создавался при работающем приложении и не являлся гарантированно атомарным снимком. Для полноценного восстановления необходима согласованная независимая резервная копия.

**Актуальность deployment:** возможности `support` / `portfolio`, авторизации и rate limiting присутствуют в текущей ветке `main`, однако их наличие и конфигурацию на работающем Railway необходимо подтвердить отдельным smoke test после развёртывания соответствующего коммита.

### Веб-интеграция

AI-консультант сайта [Glazounov AI Lab](https://glazounov-ai.ru/) отправляет запросы через серверный PHP-прокси к FastAPI backend. Прокси хранит секретный ключ вне клиентского JavaScript, валидирует запросы и применяет дополнительное ограничение частоты обращений. Режим `portfolio` предназначен для ответов по материалам о проектах и услугах.

## Тестирование и оценка качества

Автоматизированные проверки находятся в `tests/`. Они охватывают:

- маршрутизацию по режимам и валидацию API;
- авторизацию `X-API-Key`;
- ограничения частоты запросов;
- синхронизацию, обновление и удаление документов;
- реакцию на частичную запись, неполные и дублирующиеся ревизии;
- повторную индексацию при изменении параметров;
- изоляцию кеша по базе знаний и версии индекса.

Запуск из корня репозитория:

~~~powershell
python -m pytest tests -q
~~~

Для запуска тестов необходим `pytest` и зависимости проекта; `pytest` может потребоваться установить отдельно. Наличие тестов в репозитории не означает, что они выполнялись в рамках данного обновления документации.

Для экспериментальной оценки RAG предусмотрен `assistant_api/evaluate_ragas.py` с метриками Faithfulness, Context Precision и Answer Relevancy:

~~~powershell
cd assistant_api
python evaluate_ragas.py
~~~

**Ограничение методики:** текущий демонстрационный скрипт формирует `ground_truth` из части ответа самой системы, а не из независимо размеченных эталонов. Поэтому его оценки нельзя выдавать за подтверждённые показатели качества на репрезентативном датасете. Перед публикацией численных метрик необходимы независимые эталонные ответы, воспроизводимый набор вопросов и сохранённые результаты экспериментов.

## Ограничения и направления развития

Ближайшие технические задачи относятся к **основной системе `assistant_api`**:

1. Проверить соответствие production deployment текущему `main`, включая оба режима, авторизацию и ограничения запросов.
2. Ввести воспроизводимые smoke tests после deployment и фиксировать версию приложения.
3. Подготовить независимый оценочный набор для `support` и `portfolio`; измерять качество поиска и ответов до и после изменений.
4. Оценить порог релевантности, обработку отсутствующего контекста и при необходимости reranking.
5. Разработать процедуру согласованного резервного копирования и восстановления ChromaDB/SQLite.
6. Улучшить эксплуатационную наблюдаемость, контроль ошибок, затрат и времени ответа.

Это направления развития, а не заявление об уже реализованных возможностях.
