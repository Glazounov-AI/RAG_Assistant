# RAG Assistant

Два самостоятельных варианта RAG-ассистента для разных технологических сред: `assistant_api` (OpenAI) и `assistant_giga` (GigaChat). У редакций общая схема работы — поиск по документам Заказчика через ChromaDB, кэширование ответов и генерация на основе найденного контекста, — но у каждой свои config, pipeline, кэш, векторное хранилище и SQLite-журнал. Редакции не являются переключением provider внутри одного приложения; клиент может использовать любую из них независимо.

|     Проект       | LLM            | Эмбеддинги                        | Назначение             |
|------------------|----------------|-----------------------------------|------------------------|
| `assistant_api`  | OpenAI         | OpenAI (`text-embedding-3-small`) | RAG через OpenAI +     |
|                  | (`gpt-4o-mini`)|                                   |  оценка качества RAGAS |
|                  |                |                                   |                        |
| `assistant_giga` | GigaChat       | GigaChat Embeddings               | RAG через API Сбера    |


## Требования

- Python 3.14+
- Общее виртуальное окружение и общий файл зависимостей `requirements.txt`
- Общий файл `.env` в корне проекта (секреты и ключи API)

## Настройка

### Переменные окружения (`.env`)

Скопируйте шаблон и заполните ключи:

```powershell
copy .env_example .env
```

- `OPENAI_API_KEY` — нужен для `assistant_api` и `evaluate_ragas.py`
- `GIGACHAT_AUTH_KEY`, `GIGACHAT_RQUID` — нужны для `assistant_giga`
- `RAG_DB_DIR` — необязательная, только для `assistant_api`: базовый каталог хранения данных `db`. Если `RAG_DB_DIR` не задана, локально используется стандартный каталог `assistant_api/db`. При развёртывании переменная позволяет перенести базовый каталог хранения `db` на persistent storage; под этим каталогом находятся `cache`, `logs`, `chromadb` и `rate_limits`
- `RAG_RATE_LIMIT_ENABLED` — включает ограничение количества запросов к HTTP API. По умолчанию `true`.
- `RAG_API_AUTH_ENABLED` — включает проверку API-ключа для `POST /query`. По умолчанию `false`; для публичного развёртывания необходимо установить `true`.
- `RAG_API_ACCESS_KEY` — секретный ключ доступа к HTTP API. Передаётся в заголовке `X-API-Key`. При включённой авторизации отсутствие ключа в конфигурации препятствует запуску API.


### Параметры RAG (`config.py`)

В каждом проекте свой файл настроек:

- `assistant_api/config.py`
- `assistant_giga/config.py`

Основные параметры:

|         Параметр            |          Описание            |
|-----------------------------|------------------------------|
| `MODEL`                     | модель для генерации ответов |
| `EMBEDDING_MODEL`           | модель для эмбеддингов       |
| `TOP_K`                     | число документов при поиске  |
| `CHUNK_SIZE`                | размер чанка (символы)       |
| `CHUNK_OVERLAP`             | перекрытие между чанками     |
| `TEMPERATURE`, `MAX_TOKENS` | параметры генерации          |
| `LOGS_DB_PATH`              | путь к SQLite-базе логов (в обеих редакциях) |


### Режимы работы и базы знаний (`assistant_api`)

HTTP API поддерживает два режима работы, выбираемых параметром `mode`:

| Режим | Коллекция ChromaDB | Назначение | Максимальная длина запроса | Лимит запросов |
|---|---|---|---|---|
| `support` | `api_rag_collection` | Техническая поддержка | 2000 символов | 10 в минуту |
| `portfolio` | `portfolio_kb` | Информация о проектах и услугах | 8000 символов | 5 в минуту |

Настройки определяются словарём `KNOWLEDGE_BASES` в `assistant_api/config.py`.

Режим по умолчанию — `support` (`DEFAULT_MODE`).

Каждый режим использует отдельную коллекцию ChromaDB. Для `portfolio` также предусмотрен отдельный системный промпт.

Кеш ответов учитывает режим и версию базы знаний, чтобы ответы из разных режимов не смешивались.

Ограничение частоты запросов реализовано через SQLite. Лимиты применяются отдельно для каждого режима и идентификатора клиента.


### Документы для индексации

В редакции `assistant_api` используются два источника документов:

- `assistant_api/data/` — документы технической поддержки для режима `support`;
- `assistant_api/data/portfolio/` — документы о проектах и услугах для режима `portfolio`.

Поддерживаются текстовые файлы `.txt`, `.md` и `.markdown`.

При инициализации `RAGPipeline` выполняется проверка документов для обеих баз знаний.

Для `support` предусмотрено добавление новых документов. Для `portfolio` реализована синхронизация новых и изменённых документов с использованием хеша содержимого.

Коллекция `portfolio_kb` создаётся автоматически при необходимости. Наличие коллекции само по себе не означает, что в ней уже проиндексированы документы.

В редакции `assistant_giga` используется собственный каталог `data/`.

### Команды в консольном приложении

- `stats` — статистика (ChromaDB, кэш, модель)
- `clear` — очистка кэша
- `exit` / `quit` — выход


## HTTP API

Редакция `assistant_api` дополнительно предоставляет HTTP-интерфейс на FastAPI. Это параллельная точка входа рядом с консольным приложением: обе работают с одним `RAGPipeline`, кэшем и журналом запросов. У редакции `assistant_giga` HTTP-интерфейса нет.

### `GET /health`

Назначение:

- проверка доступности сервиса;
- не вызывает `RAGPipeline` для обработки пользовательского вопроса;
- не записывается в журнал пользовательских запросов.

Ответ:

```json
{
  "status": "ok",
  "service": "rag-assistant-api"
}
```


### `POST /query`

Принимает JSON с текстом вопроса и режимом работы:

```json
{
  "query": "Какие проекты представлены в портфолио?",
  "mode": "portfolio"
}
```

Параметры:

- `query` — обязательный непустой текст вопроса;
- `mode` — режим базы знаний: `support` или `portfolio`. По умолчанию `support`.

Максимальная длина запроса зависит от режима: 2000 символов для `support` и 8000 для `portfolio`.

Успешный ответ содержит поля:

- `query`
- `answer`
- `from_cache`
- `model`

Запросы через `POST /query` записываются в SQLite-журнал с `source = "api"`. Для текущего HTTP-интерфейса `user_id = NULL`, `username = NULL`. Ошибка записи в журнал не прерывает обработку HTTP-запроса.

### Авторизация HTTP API

При `RAG_API_AUTH_ENABLED=true` endpoint `POST /query` требует заголовок:

```http
X-API-Key: <секретный ключ>
```

Значение должно соответствовать переменной окружения `RAG_API_ACCESS_KEY`.

Проверка ключа выполняется до обработки запроса RAG и проверки лимита частоты. Endpoint `GET /health` остаётся общедоступным.

Секретный ключ нельзя размещать в клиентском JavaScript или публиковать в Git. Для подключения сайта предусмотрен серверный PHP-прокси.

### Ограничения и ошибки

| Код HTTP | Значение |
|---|---|
| `401` | API-ключ отсутствует или неверен при включённой авторизации |
| `422` | Ошибка валидации параметров запроса |
| `429` | Превышен лимит запросов для выбранного режима |

Ограничение частоты запросов можно отключить через `RAG_RATE_LIMIT_ENABLED=false`.

## Первый запуск RAG

При первом запуске приложение создаёт необходимые каталоги хранения и индексирует документы в ChromaDB.

В редакции `assistant_api` предусмотрены две независимые базы знаний:

- `support` — документы из `assistant_api/data/`, коллекция `api_rag_collection`;
- `portfolio` — документы из `assistant_api/data/portfolio/`, коллекция `portfolio_kb`.

При последующих запусках выполняется проверка документов. Для `support` предусмотрено добавление новых файлов, для `portfolio` — синхронизация новых и изменённых документов.

Если каталог `data/portfolio/` пуст или отсутствует, коллекция `portfolio_kb` не получает содержимое автоматически. Для работы режима необходимо подготовить и проиндексировать документы.

Каждая редакция создаёт собственный SQLite-журнал запросов в `db/logs/logs.db`.

## Как работает RAG

1. HTTP API принимает вопрос и выбранный режим `mode` (`support` или `portfolio`).
2. Проверяются авторизация (если включена), корректность параметров и лимит частоты запросов.
3. Выбираются настройки режима и соответствующая коллекция ChromaDB.
4. Проверяется кеш ответа с учётом режима и версии базы знаний.
5. Если подходящего ответа в кеше нет, создаётся эмбеддинг вопроса и выполняется поиск релевантных фрагментов в ChromaDB.
6. Найденный контекст передаётся языковой модели с системным промптом выбранного режима.
7. Сформированный ответ сохраняется в кеш и возвращается пользователю.
8. Результат обработки запроса записывается в SQLite-журнал.

Консольные приложения используют собственные точки входа. Редакция `assistant_giga` не поддерживает HTTP API и режим `portfolio`.

Данные кеша, журнала запросов и ChromaDB хранятся в каталогах соответствующих редакций. Для `assistant_api` базовый каталог можно изменить через `RAG_DB_DIR`.

## Логирование запросов

Каждая редакция ведёт свой независимый SQLite-журнал. Каталог `db/logs` создаётся автоматически и исключён из Git (`.gitignore`).

- `assistant_api/db/logs/logs.db` — журнал API-редакции (OpenAI);
- `assistant_giga/db/logs/logs.db` — журнал GigaChat-редакции.

В редакции `assistant_api` пишутся две разновидности записей: по одному на каждый реальный пользовательский вопрос из консольного приложения и из HTTP `POST /query`.

В записи сохраняются: `timestamp`, `user_id`, `username`, `source`, `query`, `response`, `from_cache`, `response_time_ms`, `created_at`.

В `assistant_api` используются два типа источника запросов: `source` = `console` для запросов через консольное приложение и `source` = `api` для запросов через HTTP `POST /query`. Для текущих console и HTTP-интерфейсов `user_id` и `username` пустые (`NULL`). Служебные команды консоли (`stats`, `clear`, `exit` / `quit`) и пустой ввод в журнал не попадают. Скрипт `evaluate_ragas.py` пользовательские запросы в `logs.db` не пишет. У `assistant_giga` HTTP-интерфейса нет — там запросы пишутся только через консольное приложение.

Ошибка записи лога не останавливает работу ассистента: это действует и для консольного приложения, и для HTTP API — ошибка логирования не прерывает обработку HTTP-запроса. В обеих редакциях механизм проверен: обычный RAG-запрос (`from_cache = 0`) и повторный идентичный запрос из кэша (`from_cache = 1`) создают отдельные записи.


## Развёртывание на Railway

В настоящее время на Railway развёрнута только редакция `assistant_api`. Редакция `assistant_giga` остаётся самостоятельной редакцией проекта и в это развёртывание не входит.

### Состояние развёртывания

На 14 октября 2026 года production-сервис Railway развёрнут из ветки `main`.

В ветке `feature/multi-knowledge-base` реализованы дополнительные возможности:

- два режима работы RAG: `support` и `portfolio`;
- независимые коллекции ChromaDB для каждого режима;
- синхронизация документов портфолио;
- проверка входных запросов и ограничения частоты обращений;
- авторизация `POST /query` через API-ключ.

Эти изменения ещё не объединены с `main` и не развёрнуты на Railway.

Для полноценного использования режима `portfolio` необходимо подготовить документы базы знаний, проверить их индексацию и выполнить тестирование.

Планируемое подключение к сайту предусматривает серверный PHP-прокси, передающий запросы к Railway без раскрытия API-ключа в браузере.

Команда запуска на Railway:

```powershell
cd assistant_api && python -m uvicorn api:app --host 0.0.0.0 --port $PORT
```

Для работы `assistant_api` на Railway используется переменная окружения `OPENAI_API_KEY` (значение ключа не публикуется).

Для постоянного хранения данных подключён Railway Volume с mount path `/data`. Для приложения установлена переменная:

```powershell
RAG_DB_DIR=/data/db
```

Поэтому данные размещаются в структуре:

```
/data/db/cache
/data/db/logs
/data/db/chromadb
```

Это позволяет сохранять SQLite-кэш, SQLite-журнал запросов и ChromaDB между redeploy контейнера.

### Проверенный перенос хранилищ на Railway Volume — 2026-10-13

**Причина переноса.** При проверке работающего контейнера обнаружено, что переменная `RAG_DB_DIR` не была задана. Данные фактически находились в `/app/assistant_api/db`, тогда как подключённый Volume `/data` содержал только служебный каталог `lost+found`. Файловая система контейнера не предназначена для сохранения этих данных между пересозданиями контейнера.

**Выполненные действия:**

1. Создан и проверен архив `rag-db-prebackup.tar.gz` с каталогами `cache`, `logs` и `chromadb`; копия архива скачана на локальный компьютер. Архив создавался при работающем приложении, поэтому является предварительной резервной копией, а не гарантированно атомарным снимком.
2. Данные скопированы в `/data/db`, выполнена повторная синхронизация при отсутствии пользовательских запросов. Копирование работающих баз само по себе не является атомарным.
3. Для сервиса `RAG_Assistant` в окружении `production` задано `RAG_DB_DIR=/data/db`; изменение применено через Railway Deploy.
4. Новый deployment перешёл в состояние **Online**. В новом контейнере подтверждены `RAG_DB_DIR=/data/db` и наличие файлов на Volume.

**Результаты проверок:**

| Проверка | Результат |
|---|---|
| SQLite `/data/db/cache/rag_cache.db` | `PRAGMA integrity_check = ok` |
| SQLite `/data/db/logs/logs.db` | `PRAGMA integrity_check = ok` |
| SQLite `/data/db/chromadb/chroma.sqlite3` | `PRAGMA integrity_check = ok` |
| ChromaDB `api_rag_collection` | Коллекция открывается, 15 документов |
| Сравнение идентификаторов документов в старой и новой ChromaDB | Количество и SHA-256 отсортированных ID совпали |
| `GET /health` после Deploy | HTTP 200 |
| Первый `POST /query` после Deploy | HTTP 200, `from_cache = false` |
| Повторный идентичный `POST /query` | HTTP 200, `from_cache = true` |
| SQLite-логи на Volume | Число записей выросло с 1 до 4; последняя запись: `source=api`, `from_cache=1`, `response_time_ms≈0.318` |

**Фактические пути production:**

```text
/data/db/cache/rag_cache.db
/data/db/logs/logs.db
/data/db/chromadb/chroma.sqlite3
/data/db/chromadb/<collection-id>/
```

**Эксплуатационные замечания:**

- Данные на подключённом Volume сохраняются при обычном redeploy, если Volume не удалён и приложение продолжает использовать `RAG_DB_DIR=/data/db`.
- Volume не заменяет независимое резервное копирование. Для восстановления необходима актуальная согласованная копия SQLite и файлов индекса ChromaDB; резервные копии рекомендуется хранить вне Railway.
- После этого переключения проверены запуск нового deployment, чтение ChromaDB, запись логов и использование кэша. **Отдельный повторный redeploy с проверкой сохранности новых записей после него в рамках этой процедуры не выполнялся.**
