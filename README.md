# RAG Assistant

**RAG Assistant** — развёрнутая система Retrieval-Augmented Generation (RAG) для поиска информации и формирования ответов на основе управляемых баз знаний. Основная реализация проекта — `assistant_api`: Python, OpenAI API, FastAPI, ChromaDB и SQLite.

Проект объединяет собственный RAG-пайплайн, синхронизацию документов с контролем ревизий, версионное кеширование, журналирование, контроль доступа и HTTP API. Сервис размещён на Railway с постоянным хранилищем и используется как backend AI-консультанта сайта [Glazounov AI Lab](https://glazounov-ai.ru/).

[**Исходный код**](https://github.com/Glazounov-AI/RAG_Assistant) · [**Документация API**](https://ragassistant-production-6923.up.railway.app/docs) · [**Health endpoint**](https://ragassistant-production-6923.up.railway.app/health)

> **Статус документа:** описание реализации `assistant_api` в ветке `main` и ранее выполненных эксплуатационных проверок. Текущую конфигурацию развёрнутого сервиса следует отличать от возможностей исходного кода.

## 1. Назначение и сценарии использования

RAG Assistant решает задачу ответов по собственным документам, когда информации из общих знаний языковой модели недостаточно либо требуется опираться на определённый набор источников.

В системе реализованы два независимых сценария:

| Режим | Для чего предназначен | Источник знаний |
|---|---|---|
| `support` | Ответы на вопросы по материалам технической поддержки | `assistant_api/data/` |
| `portfolio` | Консультирование посетителей по проектам и услугам | `assistant_api/data/portfolio/` |

Оба режима используют общую реализацию RAG-пайплайна, но отдельные коллекции ChromaDB. Для `portfolio` предусмотрены отдельные инструкции генерации: использовать факты из контекста, не придумывать проекты, клиентов, результаты, цены и сроки, не представлять демонстрационные работы как клиентские внедрения.

**Принцип системы:** документы остаются управляемым источником знаний; языковая модель получает найденные фрагменты в качестве контекста для конкретного ответа. Это не дообучение модели и не замена базы знаний параметрами LLM.

## 2. Ключевые возможности

- **Многобазовая архитектура.** Маршрутизация запросов по `mode`, независимые коллекции и настройки двух баз знаний.
- **Контролируемая индексация.** Поиск новых, изменённых и удалённых файлов, проверка SHA-256 содержимого и параметров индексации.
- **Ревизии документов.** Метаданные каждого чанка содержат источник, хеш содержимого, хеш конфигурации, идентификатор ревизии и ожидаемое число чанков.
- **Защита при синхронизации.** Новая ревизия записывается до удаления старой; предусмотрены проверки неполных ревизий и попытка очистки частично записанных данных.
- **Версионный кеш.** Ключ SQLite-кеша учитывает нормализованный вопрос, режим и состояние соответствующего индекса.
- **Две точки входа.** HTTP API на FastAPI и консольное приложение используют один `RAGPipeline`.
- **Управление доступом.** Опциональная авторизация `X-API-Key`, проверка длины запроса и SQLite rate limiting.
- **Журналирование.** Отдельная SQLite-база для запросов, ответов, признака кеша и времени обработки.
- **Постоянное хранение.** ChromaDB и SQLite вынесены на Railway Volume через `RAG_DB_DIR`.
- **Автоматизированные проверки.** В репозитории присутствуют тесты API, авторизации, лимитов и жизненного цикла индекса.

## 4. Архитектура системы

Консольное приложение и FastAPI — **две самостоятельные точки входа**. Консоль не обращается к HTTP API: обе точки входа создают и используют общий по реализации `RAGPipeline`.

```text
             Веб-клиент / внешняя интеграция       Консольный пользователь
                          |                                |
                    PHP-прокси сайта                  app.py (CLI)
                          |                                |
                    FastAPI (api.py)                        |
                валидация / API key / лимиты               |
                          |                                |
                          +---------------+----------------+
                                          |
                                    RAGPipeline
                                          |
                                 выбор режима / KB
                                          |
                           версия индекса + SQLite-кеш
                                     /         \
                              cache hit       cache miss
                                  |               |
                                  |         embedding вопроса
                                  |               |
                                  |        ChromaDB: top-k
                                  |               |
                                  |         контекст + промпт
                                  |               |
                                  |          OpenAI Chat API
                                  |               |
                                  |          запись в кеш
                                  +-------+-------+
                                          |
                                         ответ
                                          |
                               SQLite-журнал точки входа
```

### Ответственность компонентов

| Компонент | Файл | Функция |
|---|---|---|
| HTTP API | `assistant_api/api.py` | Маршруты, валидация, авторизация, лимиты и HTTP-ответы |

| RAG | `assistant_api/rag_pipeline.py` | Выбор базы знаний, кеш, retrieval, промпт, генерация |
| Векторное хранилище | `assistant_api/vector_store.py` | Индексация, ревизии, embeddings, поиск |
| Кеш | `assistant_api/cache.py` | Хранение и получение ответов |
| Журнал | `assistant_api/db_logger.py` | Запись запросов и времени обработки |
| Rate limiter | `assistant_api/rate_limiter.py` | Транзакционный учёт минутных квот |

| Оценка | `assistant_api/evaluate_ragas.py` | Экспериментальный сценарий RAGAS |

## 5. RAG Pipeline: от вопроса до ответа

Обработка запроса проходит последовательные этапы.

1. **Выбор базы знаний.** `mode` определяет коллекцию и набор инструкций. Если режим не указан, используется `support`.
2. **Определение версии индекса.** Пайплайн вычисляет версию выбранной коллекции по сохранённым идентификаторам чанков и метаданным.
3. **Проверка кеша.** При наличии записи с совпадающими вопросом, режимом и версией индекса ответ возвращается без повторного поиска и генерации.
4. **Семантический поиск.** При промахе кеша запрос преобразуется в embedding; ChromaDB возвращает до `TOP_K` ближайших фрагментов.
5. **Формирование контекста.** Тексты найденных фрагментов включаются в пользовательский промпт. Системный промпт выбирается по режиму.
6. **Генерация.** OpenAI формирует ответ с заданными параметрами модели.
7. **Сохранение результата.** Ответ и контекст записываются в SQLite-кеш, затем точка входа возвращает ответ и пытается создать запись в журнале.

### Параметры RAG

| Параметр | Значение в `config.py` | Значение для системы |
|---|---|---|
| `MODEL` | `gpt-4o-mini` | Модель генерации |
| `EMBEDDING_MODEL` | `text-embedding-3-small` | Модель векторизации |
| `TOP_K` | `3` | Максимальное число возвращаемых фрагментов |
| `CHUNK_SIZE` | `500` | Целевой размер чанка в символах |
| `CHUNK_OVERLAP` | `100` | Целевое перекрытие |
| `MIN_CHUNK_SIZE` | `50` | Параметр обработки коротких чанков |
| `TEMPERATURE` | `0.3` | Параметр генерации |
| `MAX_TOKENS` | `500` | Максимум токенов ответа |

Разбиение учитывает абзацы и предложения, стремясь сохранять связность текста. `CHUNK_SIZE` — **целевой**, а не безусловный жёсткий предел для любого входного текста. При создании новой коллекции ChromaDB задаётся косинусное расстояние.

## 6. Управление базами знаний и жизненный цикл индекса

### Конфигурация баз знаний

| Режим | Каталог | Коллекция | Максимальная длина вопроса | Лимит запросов |
|---|---|---|---:|---:|
| `support` | `assistant_api/data/` | `api_rag_collection` | 2 000 символов | 10/мин |
| `portfolio` | `assistant_api/data/portfolio/` | `portfolio_kb` | 8 000 символов | 5/мин |

Параметры задаются словарём `KNOWLEDGE_BASES`. Поддерживаются файлы `.txt`, `.md`, `.markdown`. Индексируются файлы непосредственно в каталоге соответствующей базы знаний; вложенный `portfolio/` обрабатывается отдельно как собственная KB.

### Индексация и синхронизация

При создании `RAGPipeline` выполняется синхронизация обеих баз. Поэтому обновление исходных документов само по себе **не означает мгновенного обновления работающего индекса**: новая проверка происходит при следующей инициализации или явном вызове механизма синхронизации.

Система использует следующие механизмы:

1. **Контроль содержимого.** SHA-256 документа позволяет определить, изменился ли текст.
2. **Контроль параметров.** Хеш конфигурации учитывает модель embeddings и параметры chunking; изменение настроек может инициировать повторную индексацию.
3. **Учёт ревизий.** Чанки получают идентификаторы, связанные с документом, ревизией и порядковым номером.
4. **Проверка полноты.** Сопоставляются ожидаемое количество чанков и фактические идентификаторы сохранённой ревизии.
5. **Повторное использование индекса.** Если подходящая полная ревизия уже существует, повторные embeddings не создаются без необходимости.
6. **Замена документа.** Новые чанки записываются до удаления предыдущих.
7. **Обработка удаления.** Записи удалённых из каталога документов удаляются из индекса.
8. **Защита от массового удаления.** Если исходный каталог полностью пуст, а в индексе есть документы, операция очистки всей базы блокируется.

При ошибке записи новых чанков выполняется попытка удалить частично добавленную ревизию, сохраняя старую. Это **защитный алгоритм**, а не гарантия полной транзакционной атомарности ChromaDB при любых отказах.

### Версия индекса и согласованность кеша

Версия индекса рассчитывается из фактически сохранённых данных коллекции. Изменение набора чанков или значимых метаданных приводит к другой версии. Благодаря этому кешированный ответ не используется для изменённой базы знаний только на основании совпадения текста вопроса.

## 7. Кеширование

SQLite-кеш хранит вопрос, ответ, контекст и время создания записи. Ключ вычисляется как SHA-256 от комбинации:

```text
mode : kb_version : normalized_query
```

Нормализация приводит текст вопроса к нижнему регистру, удаляет лишние пробелы по краям и сворачивает повторяющиеся пробелы.

Это даёт два существенных свойства:

- ответы разных баз знаний не смешиваются;
- после изменения индекса прежние ответы не попадают в кеш текущей версии KB.

**Граница механизма:** версия кеша отражает состояние индекса, но не все параметры генерации. Изменение модели или промпта без изменения индекса само по себе не гарантирует новый ключ. В консоли предусмотрена команда `clear` для полной очистки кеша. Автоматический срок жизни записей в текущей реализации не установлен.

## 8. HTTP API и безопасность

HTTP API реализован на FastAPI. Интерактивная схема доступна по `/docs`.

### `GET /health`

Проверка доступности HTTP-сервиса:

```json
{
  "status": "ok",
  "service": "rag-assistant-api"
}
```

Маршрут не запускает RAG-запрос и не пишет запись в журнал пользовательских вопросов. Это **liveness-проверка HTTP-приложения**, а не независимый тест OpenAI, поиска или качества ответа.

### `POST /query`

Пример:

```http
POST /query
Content-Type: application/json
X-API-Key: <ключ, если включена авторизация>
```

```json
{
  "query": "Какие проекты представлены в портфолио?",
  "mode": "portfolio"
}
```

Поля запроса:

- `query` — обязательная непустая строка; пробелы по краям удаляются;
- `mode` — `support` или `portfolio`; по умолчанию `support`.

Пример структуры успешного ответа:

```json
{
  "query": "Какие проекты представлены в портфолио?",
  "answer": "<ответ на основе найденного контекста>",
  "from_cache": false,
  "model": "gpt-4o-mini"
}
```

Это **пример структуры**, а не зафиксированный ответ работающего сервиса.

| HTTP-код | Условие |
|---|---|
| `200` | Ответ успешно сформирован |
| `401` | Нет действительного API-ключа при включённой авторизации |
| `422` | Ошибка схемы, режима или длины вопроса |
| `429` | Превышен лимит обращений |
| `500` | Ошибка обработки RAG-запроса |

### Авторизация

Управляется переменными:

```dotenv
RAG_API_AUTH_ENABLED=true
RAG_API_ACCESS_KEY=<секретный-ключ>
```

Ключ передаётся в `X-API-Key` и сравнивается с настроенным значением через `secrets.compare_digest`. Проверка происходит до обращения к RAG-пайплайну. Если авторизация включена, но секрет не задан, запуск HTTP-приложения прерывается.

**Важно:** в исходных настройках `RAG_API_AUTH_ENABLED=false`. Для публичного доступа режим защиты должен быть включён в окружении развёртывания. Секреты нельзя размещать в репозитории или клиентском JavaScript.

### Rate limiting

При `RAG_RATE_LIMIT_ENABLED=true` действует SQLite-ограничитель с минутными окнами. Учёт разделён по идентификатору клиента и режиму; лимиты заданы в `KNOWLEDGE_BASES`.

Вместо счётчика в памяти применяется транзакция SQLite `BEGIN IMMEDIATE`: проверка и увеличение счётчика выполняются под блокировкой записи. Заблокированный запрос не увеличивает счётчик успешных допусков. Устаревшие окна удаляются.

HTTP API определяет идентификатор клиента через `request.client.host`. При работе через общий серверный прокси несколько конечных посетителей могут учитываться как один клиент на стороне backend; это особенность схемы идентификации, которую необходимо учитывать при эксплуатации.

## 9. SQLite, журналирование и наблюдаемость

По умолчанию все локальные данные `assistant_api` находятся в `assistant_api/db/`. Каталог можно переопределить переменной `RAG_DB_DIR`:

```text
db/
├── cache/
│   └── rag_cache.db
├── logs/
│   └── logs.db
├── chromadb/
│   ├── chroma.sqlite3
│   └── <данные коллекций>
└── rate_limits/
    └── rate_limits.db
```

### Журнал запросов

Каждый обработанный пользовательский вопрос через CLI или `POST /query` записывается в отдельную SQLite-базу, если журнал доступен.

| Поле | Содержание |
|---|---|
| `timestamp`, `created_at` | Временные метки |
| `source` | `console` или `api` |
| `query`, `response` | Вопрос и ответ |
| `from_cache` | Признак кешированного ответа |
| `response_time_ms` | Время выполнения `pipeline.query()` |
| `user_id`, `username` | Зарезервированные поля; в текущих CLI и HTTP-запросах не заполняются |

Для каждого реального запроса формируется отдельная запись, в том числе при ответе из кеша. Служебные команды консоли и `GET /health` не создают записи пользовательского запроса. Скрипт RAGAS не использует этот журнал как интерфейс пользовательских обращений.

Ошибки инициализации или записи журнала не должны прерывать выдачу ответа: соответствующие исключения обрабатываются в точках входа. Время `response_time_ms` измеряет вызов RAG-пайплайна, а не полное время HTTP-запроса с сетевыми задержками.

**Работа с данными:** журнал содержит тексты запросов и ответов. Доступ к файлам, резервным копиям и срокам хранения должен соответствовать характеру обрабатываемой информации.

## 10. Установка, настройка и локальный запуск

### Требования

- Python 3.14 — версия, использованная в конфигурации разработки проекта;
- доступ к OpenAI API и переменная `OPENAI_API_KEY`;
- зависимости из `requirements.txt`;
- возможность записи локальных SQLite-файлов и каталога ChromaDB.

Совместимость конкретного окружения зависит от установленных версий зависимостей. Для Railway предусмотрен отдельный сокращённый набор `requirements-railway.txt`.

### Установка на Windows / PowerShell

Из каталога для проектов:

```powershell
git clone https://github.com/Glazounov-AI/RAG_Assistant.git
cd RAG_Assistant

py -3.14 -m venv venv_py314
.\venv_py314\Scripts\Activate.ps1
python -m pip install -r requirements.txt

Copy-Item .env_example .env
```

Откройте `.env` и задайте действительный `OPENAI_API_KEY`. Остальные строки шаблона, не относящиеся к `assistant_api`, для запуска основной системы не требуются. **Не публикуйте `.env` и реальные ключи в Git.**

### Локальный HTTP API

```powershell
cd assistant_api
python -m uvicorn api:app --host 127.0.0.1 --port 8000
```

Проверка:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health
```

Запрос к `support`:

```powershell
$body = @{
    query = "Что такое RAG?"
    mode  = "support"
} | ConvertTo-Json

Invoke-RestMethod `
    -Uri "http://127.0.0.1:8000/query" `
    -Method Post `
    -ContentType "application/json" `
    -Body $body
```

При включённой авторизации добавьте заголовок `X-API-Key` с настроенным секретом.

### Консольное приложение

Из каталога `assistant_api`:

```powershell
python app.py
```

Команды:

| Команда | Назначение |

При следующих инициализациях система проверяет изменения исходных файлов и параметров индексации. Повторное создание embeddings для неизменённых корректных ревизий не требуется.

### Постоянное хранение

Для production подключён Railway Volume с точкой монтирования `/data`. Установлено:

```dotenv
RAG_DB_DIR=/data/db
```

Таким образом, данные кеша, журнала и ChromaDB хранятся вне эфемерной файловой системы контейнера и сохраняются при обычном redeploy, пока подключён тот же Volume и не изменён путь данных.

### Проверенный перенос данных — 13 октября 2026 года

При проверке предыдущего deployment было установлено, что базы находились в файловой системе контейнера, хотя Volume был подключён. Для перевода данных на постоянное хранилище выполнены предварительное резервное копирование, перенос в `/data/db`, настройка `RAG_DB_DIR` и новый deployment.

| Объект / операция | Зафиксированный результат |
|---|---|

Эти результаты подтверждают **состояние на дату проверки**. Они не доказывают автоматически, что каждый последующий коммит `main` развёрнут и проверен в production.

### Интеграция с веб-сайтом

Сайт [Glazounov AI Lab](https://glazounov-ai.ru/) использует серверный PHP-прокси для обращения к backend. Посетитель работает с интерфейсом сайта, а Python-сервис отдельно обрабатывает запросы и возвращает ответы. Сценарий консультации по проектам использует режим `portfolio`.

Это разделение позволяет размещать фронтенд на PHP-хостинге, который не запускает Python-приложения, а RAG backend — на отдельной платформе. Секреты backend должны оставаться на серверной стороне.

### RAGAS

В `assistant_api/evaluate_ragas.py` предусмотрен экспериментальный сценарий оценки с метриками:

- **Faithfulness** — соответствие ответа переданному контексту;
- **Context Precision** — качество извлечённого контекста;
- **Answer Relevancy** — соответствие ответа вопросу.

Запуск:

```powershell
cd assistant_api
python evaluate_ragas.py
```

Скрипт использует демонстрационные вопросы и формирует `ground_truth` из части собственного ответа пайплайна, а не из независимо подготовленных эталонов. Поэтому его результаты не следует трактовать как подтверждённые показатели качества на независимом датасете. **Численные метрики качества в README не приводятся, поскольку воспроизводимые результаты здесь не представлены.**

### Подтверждённые эксплуатационные проверки

В ходе ранее проведённых работ зафиксированы: успешные ответы `/health` и `/query`, попадание повторного запроса в кеш, сохранение кеша после redeploy, работоспособность SQLite-журнала и проверка целостности хранилищ после переноса на Railway Volume.

## 13. Границы реализации

README фиксирует реализованную систему и условия её работы:

- Поиск использует ближайшие фрагменты ChromaDB (`TOP_K`) без отдельного reranker и явного порога релевантности.
- Инструкции LLM требуют отвечать по контексту, но не дают математической гарантии отсутствия ошибок.
- Синхронизация выполняется при инициализации пайплайна или явном вызове; автоматическое отслеживание изменений файлов в реальном времени не реализовано.
- Замена ревизий защищает старые данные при ряде ошибок, но не является атомарной транзакцией для всех операций ChromaDB.
- Ключ кеша учитывает состояние индекса, но не все параметры генерации.
- API возвращает текст ответа и служебные поля, но не отдельный список цитируемых источников.
- `GET /health` проверяет HTTP-приложение, а не полную цепочку RAG.
- SQLite-журнал содержит тексты запросов и ответов; режим хранения и доступ к данным требуют соответствующей эксплуатационной политики.

Это границы **существующей реализации**, а не план переписывания кода.
