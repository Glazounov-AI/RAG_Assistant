# Client Request Normalizer — нормализация клиентских запросов с помощью LoRA

**Тип проекта:** NLP, Fine-Tuning, LoRA, Structured Data Extraction, машинное обучение
**Статус:** завершённый эксперимент LoRA v1, демонстрационный прототип
**Предметная область:** компьютерная техника и IT-услуги
**Репозиторий:** проект Client Request Normalizer в GitHub-портфолио Glazounov-AI

## Назначение проекта

Client Request Normalizer — экспериментальный компонент для преобразования русскоязычных обращений клиентов из свободного текста в структурированный JSON.

Проект исследует, насколько дообучение компактной языковой модели с использованием LoRA повышает качество определения намерения клиента и извлечения параметров запроса.

Полученные структурированные данные потенциально могут использоваться в CRM, чат-ботах, каталогах товаров и системах обработки заявок.

Проект не является готовой производственной CRM или чат-ботом.

## Решаемая задача

Клиенты формулируют обращения неформально:

- «Сколько стоит установить Windows на два ноутбука?»
- «Нужно настроить Wi-Fi в офисе на следующей неделе».
- «Есть три SSD Samsung по 1 ТБ?»

Для автоматизации дальнейшей обработки необходимо определить цель обращения и извлечь сведения, явно присутствующие в тексте.

Модель должна возвращать один JSON-объект с семью обязательными полями:

- `intent` — намерение клиента;
- `item_type` — товар или услуга;
- `item` — нормализованное наименование;
- `brand` — указанный бренд;
- `quantity` — количество;
- `location` — место;
- `deadline` — срок.

Поддерживаются четыре категории намерений:

- `price_request` — запрос стоимости;
- `service_order` — заказ услуги;
- `availability_request` — запрос наличия товара;
- `unknown` — неподдерживаемое или неоднозначное обращение.

Отсутствующие или неоднозначные сведения должны возвращаться как `null`. Модель не должна придумывать данные.

## Пример работы

**Запрос клиента:**

«Сколько стоит установить Windows на два ноутбука?»

**Ожидаемый структурированный результат:**

```json
{
  "intent": "price_request",
  "item_type": "service",
  "item": "установка Windows",
  "brand": null,
  "quantity": 2,
  "location": null,
  "deadline": null
}
```

Это пример эталонного результата по схеме проекта, а не гарантия, что модель всегда выдаёт правильный JSON.

## Технологии

- Python 3.12.
- PyTorch и CUDA.
- Hugging Face Transformers.
- PEFT и LoRA.
- Hugging Face Datasets.
- Accelerate.
- JSON Lines для хранения обучающих примеров.
- Git для версионирования кода, данных и результатов эксперимента.

**Базовая модель:** `Qwen/Qwen2.5-0.5B-Instruct`.

**Оборудование:** NVIDIA GeForce RTX 3050 с 8 ГБ видеопамяти.

Обучение и тестирование выполнялись локально.

## Подготовка данных

Для версии v1 подготовлен синтетический датасет из 120 русскоязычных запросов.

| Набор | Количество | Назначение |
|---|---:|---|
| Train | 90 | Обучение LoRA |
| Validation | 15 | Контроль в процессе обучения |
| Test | 15 | Независимое сравнение моделей |

Примеры составлялись вручную и по шаблонам. Наборы разделены по назначению.

Все 120 записей прошли структурную проверку валидатором проекта.

При этом синтетический характер данных, небольшой объём тестовой выборки и возможное семантическое сходство примеров ограничивают достоверность обобщения результатов.

## Дообучение модели

Для адаптации базовой Qwen2.5-0.5B-Instruct использовался метод LoRA.

Параметры эксперимента v1:

- 3 эпохи обучения;
- 69 шагов оптимизации;
- LoRA rank 8;
- LoRA alpha 16;
- FP16;
- накопление градиентов.

LoRA позволяет обучать сравнительно небольшое количество дополнительных параметров без полного обновления всех весов базовой модели.

Адаптер сохранялся отдельно от исходной модели.

## Методика сравнения

Сравнивались две конфигурации:

**Baseline** — исходная Qwen2.5-0.5B-Instruct без предметного дообучения.

**LoRA v1** — та же базовая модель с обученным LoRA-адаптером.

Обе конфигурации проверялись на одинаковых 15 тестовых запросах с одинаковыми параметрами генерации, включая `do_sample=False`.

Оценивались корректность JSON, соответствие схеме, точность определения намерения, точность извлечения полей и полное совпадение с эталоном.

## Результаты эксперимента

| Метрика | Baseline | LoRA v1 |
|---|---:|---:|
| JSON Validity | 93,3% | 100,0% |
| Schema Validity | 66,7% | 73,3% |
| Intent Accuracy | 53,3% | 93,3% |
| Field Accuracy | 39,1% | 85,7% |
| Exact Match | 0,0% | 46,7% |

Исходные абсолютные значения:

- Корректный JSON: 14 из 15 против 15 из 15.
- Соответствие схеме: 10 из 15 против 11 из 15.
- Правильное намерение: 8 из 15 против 14 из 15.
- Правильные поля: 41 из 105 против 90 из 105.
- Полное совпадение с эталоном: 0 из 15 против 7 из 15.

На тестовом наборе дообучение существенно улучшило определение намерения и извлечение полей.

Однако даже LoRA v1 не обеспечила полного соблюдения схемы: четыре из 15 ответов не прошли проверку Schema Validity.

Результаты являются показателями небольшого экспериментального набора, а не подтверждёнными производственными характеристиками.

## Ограничения

1. Датасет состоит из 120 синтетических примеров; тестовый набор содержит только 15 запросов.
2. Не проведена проверка на репрезентативной выборке реальных клиентских обращений.
3. Схема v1 рассчитана на одну основную товарную или сервисную позицию.
4. Обращения с несколькими независимыми позициями могут обрабатываться некорректно.
5. Возможны ошибки нормализации наименований, определения места и заполнения полей.
6. Корректный JSON не гарантирует соответствия заданной схеме или смысловой правильности.
7. В версии v1 отсутствует производственная интеграция с CRM, каталогом товаров или системой исполнения заказов.
8. Модель не проверяет наличие товаров, не рассчитывает цены и не выполняет транзакции.

## Практическая ценность

Проект демонстрирует применение параметроэффективного дообучения компактной LLM к прикладной задаче извлечения структурированных данных.

Потенциальные направления использования:

- предварительная классификация клиентских обращений;
- извлечение параметров заказа;
- подготовка структурированных записей для CRM;
- маршрутизация запросов;
- передача извлечённых данных в последующую бизнес-логику.

Для реального применения необходимы серверная интеграция, строгая проверка выходной схемы, обработка ошибок, дополнительные тесты и контроль качества на реальных данных.

## Дальнейшее развитие

Планируемые направления:

- расширение и ревизия датасета;
- поддержка нескольких товарных позиций в одном запросе;
- расширение схемы характеристик;
- улучшение соблюдения JSON-схемы;
- API для интеграции;
- интеграция с каталогом товаров и CRM;
- уточняющие вопросы при недостатке информации;
- проверка качества на реальных обращениях.

Перечисленные возможности не реализованы в экспериментальной версии LoRA v1.

## Краткий ответ для посетителя портфолио

Client Request Normalizer — проект по дообучению компактной модели Qwen2.5-0.5B-Instruct методом LoRA для извлечения структурированных данных из русскоязычных клиентских запросов.

На экспериментальном тестовом наборе из 15 запросов точность определения намерения выросла с 53,3% до 93,3%, а точность извлечения полей — с 39,1% до 85,7%.

Проект демонстрирует методику локального дообучения и измеримого сравнения моделей. Это исследовательский прототип, не готовая производственная система.
